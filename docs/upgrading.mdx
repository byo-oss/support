Each section covers one release, newest first. Read the sections between your current version and the latest. The docs describe the latest published release. Sections marked next describe main, which isn't published yet.

## 0.5.0

Upgrading from 0.4.x needs no migration and no API change. The schema didn't change and no export, option or endpoint changed. Breaking under the conventions (§8.4) because the zod and vitest peers narrowed. The `@byo-oss/core`, postal-mime and mailauth dependency floors rose too.

- **The zod peer floor is now `^4.6.6`.** zod 4.6.6 fixes GHSA-mrhx-c7xc-m3w5 (high severity). Support validates request input with your app's copy of zod, so that copy needs 4.6.6 or later. Move it before or with this package:

  ```sh
  npm install zod@latest @byo-oss/support@latest
  ```

- **`@byo-oss/core` is now `^0.2.0`.** It is a dependency of this package, not a peer. Core 0.2.0 only narrowed its better-auth peer to `^1.7.16`, which this package already requires. If your app also imports `@byo-oss/core` or `@byo-oss/notifications`, move them to releases that use core 0.2.0, so your package manager installs one copy of core instead of two.

- **The optional `vitest` peer floor is now `>=4.1.11`.** This closes GHSA-5xrq-8626-4rwp (critical, affects vitest below 3.2.6 and 4.0.x) and GHSA-82fw-gwwq-j7x9 (moderate, affects below 4.1.11), and drops vitest 3. Only the `@byo-oss/support/testing` entry point uses vitest, but the narrowed peer applies to every app that has vitest installed: it needs 4.1.11 or later even if it never imports `./testing` (npm stops with `ERESOLVE`). Move vitest before or with this package.

- **`postal-mime` is now `^4.2.1` and `mailauth` is `^8.0.6`.** Both are dependencies of this package, used only for inbound email. postal-mime 4.2.1 fixes GHSA-jh3p-792r-98gm and GHSA-q8wm-54mj-r36p, which affect every version up to 4.2.0 (they are listed on the postal-mime repository, so `npm audit` doesn't show them). mailauth 8.0.6 brings joi 18.3.2, which fixes GHSA-4528-x5fx-h6hg. The newer postal-mime reads some mail differently. That covers malformed mail (header block end, boundary matching, base64 or quoted-printable `message/rfc822` parts kept as attachments), and in well-formed mail the text of inline forwarded messages and text taken from HTML with multi-line `<style>`/`<script>` blocks. Support stores `email.text`, so those messages can read differently. Apps that only use the package's inbound sources don't need to change anything.

## 0.4.0

Upgrading from 0.3.x needs no migration and no API change. The schema didn't change. One peer range is narrower, and one behaviour changes because of better-auth.

- **The better-auth peer floor is now `^1.7.16`.** `better-auth` and `@better-auth/core` both need 1.7.16 or later, because 1.7.16 is a security release. Move `better-auth` and every `@better-auth/*` package in your app together to 1.7.16 or later, before or with this package:

  ```sh
  npm install better-auth@latest @better-auth/core@latest @byo-oss/support@latest
  ```

  The advisory that touches this package's features is GHSA-c85h-5mrr-mgx4 (organization roles with padded names), because your agents are members of the staff organization. See the [better-auth security release](https://better-auth.com/blog/security-release-2026-11-03) for the rest.

- **Role values are trimmed and split on commas.** This comes from better-auth 1.7.16, not from this package. Support passes a staff member's stored role to the organization plugin's `hasPermission`, which now trims it and splits it on commas. A staff member stored as `"admin, owner"` now has the permissions of both roles, owner included, so they may gain `support` actions they didn't have. Before you upgrade, look for padded or comma-separated role values in the staff organization's `member` rows (and in pending `invitation` rows), and fix any that grant more than you intended.

## 0.3.0

Upgrading from 0.2.0 needs no migration. The schema didn't change, and the package's peer dependencies are the same. Three things change for users.

- **Category cards are on by default.** The widget's New ticket form, and its empty list, now show a card per kind of support: "Ask a question", "Report a bug", "Suggest a feature" and "Talk to us". A new ticket gets the chosen kind as a tag, and the tag is set before `support.ticket.created` fires. To keep the form as it was, set `categories: false`:

  ```ts title="lib/auth.ts"
  support({ staffOrganizationId, categories: false });
  ```

  The create endpoint accepts a `category` and answers 400 `INVALID_CATEGORY` for a kind that isn't offered. The list responses add `features.categories`.

- **Default wording changed.** The widget names statuses in the customer's words: "With our team" for open, and "Awaiting your reply" for pending. Before, it showed "Open" and "Pending". Solved and Closed are unchanged. To keep the old names, set them in the components' `labels.customerStatus` prop:

  ```tsx
  <SupportWidget labels={{ customerStatus: { open: "Open", pending: "Pending" } }} />
  ```

  The inbox's "Status after sending" select is replaced by a Send and solve button and a send menu with Send and keep open and Send and close. Attach and Mention are now icon buttons with accessible labels. No label key was renamed or removed, and the new keys have English defaults.

- **New inbox behaviour, on by default.** Keyboard shortcuts (j, k, /, r, n, e, ?) are on, and each agent can turn them off from the `?` sheet. Drafts are kept per ticket while the inbox is mounted. Queue rows show how long a customer has waited on an open ticket. The agent queue filters by `requesterId` and `requesterEmail`, and `useSupportQueue` takes the same filters.

## 0.2.0

Upgrading from 0.1.0 has two changes.

- **Events fire after the write commits.** `onEvent` used to run as soon as its write returned, even inside the caller's transaction. Endpoint writes don't join a caller's transaction, so their events still follow at once. Writes made inside `runWithTransaction` now queue their events until the transaction commits, and drop them if it rolls back. If your handler assumed it ran before commit, check that assumption. See [Events](/docs/support/events#when-an-event-fires).

- **`@better-auth/core` is a new required peer.** Install it at the same version as `better-auth`. better-auth already depends on it, so this only matters when your package manager is strict about peers.

  ```sh
  npm install @better-auth/core
  ```
